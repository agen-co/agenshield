AgenShield installed and `agenshield status` answers — but the device is
nowhere in the Frontegg Portal. The campaign may show **Script fetched**
without **Registration**.

The software is installed. It just does not know which organization it belongs to.

For a managed Windows installation, go directly to
[Windows managed installations](#windows-managed-installations). The account
and `root` explanations below apply to macOS, not Windows machine policy.

## Confirm it is this

For macOS, on the affected Mac:

```bash
agenshield status
```

Under **Cloud**, an enrolled device names your backend URL and shows a device
identity. An unenrolled one reports that setup is incomplete or that no cloud
credentials exist.

The install log names every place it looked for your enrollment details:

```bash
sudo grep -A 7 'No enrollment tokens found' /var/log/agenshield/install.log
```

That block lists each source it checked and which user's home it checked against.
If it names a home that is not the one the person actually signs in with — most
often `/var/root` — you have this problem.

## The usual cause: the install ran as `root`, for a different account

AgenShield keeps per-user state in the signed-in user's home. Before release
**2026.9**, the install command worked that directory out from the environment it
happened to inherit. Run by a person in their own Terminal, that was right. Run by
an MDM script runner — JumpCloud Commands, a Kandji custom script, a Mosyle custom
command, a Jamf policy script, or over SSH — the environment belongs to `root`, so
the enrollment details were staged into `root`'s home and the installer looked for
them in the signed-in user's. Nothing matched, and nothing said so: the install
reported success.

Two other causes produce the same symptom:

| Also check                    | What it looks like                                                                                                                               |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **The profile never arrived** | Package-only MDM deployments take their enrollment details from the configuration profile. If it did not land, there was nothing to enroll with. |
| **The campaign was revoked**  | A revoked campaign refuses new enrollments. Already-enrolled devices are unaffected, which is why only new machines show the symptom.            |

## Fix it

<Steps>
  <Step title="Upgrade to 2026.9 or later">
    Releases from 2026.9 resolve the signed-in user themselves, so an install run
    as `root` with nobody at a terminal enrolls correctly with no wrapper. They
    also **fail loudly** — the command exits non-zero — when a device does not
    finish enrolling, so a green result in your MDM means the device is really on
    your fleet.

    ```bash
    curl -fsSL 'https://<your-backend-url>/resources/campaigns/v1/<campaign-token>/install.sh' | bash
    ```

  </Step>
  <Step title="Or enroll the machine in place">
    The software is already installed and does not need reinstalling. Run this as
    the person who signs in to the Mac, with the token from your campaign:

    ```bash
    agenshield setup --token <CAMPAIGN_TOKEN> --cloud-url https://<your-backend-url>
    ```

    From 2026.9.1 the person at the Mac can do the same without a terminal: the
    AgenShield dashboard shows an enrollment screen on a Mac that is not
    registered, with a field for the token (and for your backend URL, if the Mac
    has none recorded). The menubar panel carries the same field.

  </Step>
  <Step title="Confirm">
    The device appears under **Devices** in the Frontegg Portal within a minute,
    and the campaign timeline gains a **Registration** entry.
  </Step>
</Steps>

## If the Mac has several accounts

Name the one AgenShield should install for, rather than letting the installer
choose:

```bash
export AGENSHIELD_TARGET_USER='jdoe'
curl -fsSL 'https://<your-backend-url>/resources/campaigns/v1/<campaign-token>/install.sh' | bash
```

## A Mac with nobody signed in is a different case

On a freshly imaged Mac sitting at the login window there is no account to install
for yet. That device still enrolls, and its extensions activate at the first
login — the same as a package deployment. That is expected, not this problem. See
[MDM enrollment](../deployment/mdm/overview.mdx#how-a-device-joins-your-fleet).

## Enrollment is waiting on the management profile

The AgenShield dashboard or menu bar panel says **Enrollment is waiting on this
device's management profile** (on a Mac, **this Mac's**), and the device is not
in the Frontegg Portal.

AgenShield has enrollment details for this device, but it cannot read the
device's management profile, which it needs before it can use them. Rather than
guess, it holds the enrollment, and the device is not protected until it
completes. AgenShield keeps checking every few minutes, but an unreadable
profile does not repair itself.

Ask IT to do one of these:

- **Re-push the management profile.** Reinstall the AgenShield configuration
  profile from your MDM. On Windows, re-apply the configuration profile or Group
  Policy that sets `HKEY_LOCAL_MACHINE\SOFTWARE\Policies\Frontegg\AgenShield`
  for this computer.
- **Re-run the AgenShield installer** with your campaign's install command or
  package.

Nobody needs to be at the device: enrollment continues on its own once the
profile can be read. Confirm it the same way — the device appears under
**Devices** and the campaign gains a **Registration** entry.

## Windows managed installations

A silent Windows MSI or tokenless unattended bootstrap can install successfully
before enrollment policy arrives. That installer result is not a promise that the
device registered. No signed-in user is required for Windows machine enrollment.

Check these in order:

1. **Enrollment status.** Run `agenshield status`. Under **Cloud**, confirm the
   expected cloud URL and device identity, or note that setup is incomplete.
2. **Policy assignment.** Confirm the Windows configuration profile or Group
   Policy applies to this **computer**, not just a user. Intune app and profile
   assignments must target the same intended devices.
3. **Complete values.** The 64-bit machine key
   `HKEY_LOCAL_MACHINE\SOFTWARE\Policies\Frontegg\AgenShield` needs both
   `CampaignToken` and `CloudUrl` as strings. They must be supplied together;
   a token in one source is not combined with a cloud URL in another.
4. **Active campaign and connectivity.** Confirm the campaign is not revoked,
   and that the device can reach the campaign's cloud URL. For a tokenless
   install, a release download alone does not supply enrollment credentials.
5. **Intentional enrollment opt-out.** On releases with managed enrollment
   opt-out, an administrator-created
   `%ProgramData%\AgenShield\config\ignore-managed-enrollment` file suppresses
   managed enrollment. Ask IT whether it is intentional. Removing that file
   re-enables reading the enrollment policy; do not weaken the directory's
   permissions. The policy may still be shown as present while enrollment is
   intentionally disabled.

Repair the assigned settings rather than repeatedly reinstalling. AgenShield
retries after complete policy arrives. If the installation used MSI token
properties, prefer the managed policy or the campaign's Windows install link;
see [Windows install warnings](../troubleshoot/windows-install-warnings.mdx).

### Already enrolled with a different cloud URL

Managed settings are an initial enrollment channel, not an automatic migration
mechanism. An already-enrolled device is not re-registered or repointed when a
different campaign policy arrives. A reported enrollment endpoint conflict
means the new policy disagrees with the existing enrollment.

Have IT correct the assignment or perform the approved offboarding and
re-enrollment process. Do not delete credentials or change protected files to
force a migration. Removing policy alone does not unenroll an existing device.

### Confirm recovery

Confirm a **Registration** entry and the expected device in the Frontegg Portal,
then confirm the device received your organization's policy and has no outstanding
protection required action. Installation, registration, and active protection
are separate results. Exact settings and deployment choices are in
[Windows MDM deployment](../deployment/mdm/windows.mdx).

## Escalate

If enrollment still does not complete, collect a diagnostics bundle and open a
ticket:

```bash
agenshield doctor --bundle
```

See [Collecting diagnostics](../troubleshoot/collecting-diagnostics.mdx). Never paste a
raw enrollment token into a ticket — reference the campaign by name instead.
